## ✔ [blocant] (securitate) Funcțiile de amprentă SECURITY DEFINER rămân apelabile de anon (REVOKE doar FROM PUBLIC) — oracle/scurgere pontaj fără login
- **Unde**: `supabase/migrations/20260930h_diurna_salveaza_plata.sql:65 (și :72, :149-150)`
- **Scenariu**: Supabase acordă implicit (ALTER DEFAULT PRIVILEGES … GRANT ALL ON FUNCTIONS TO anon, authenticated, service_role) EXECUTE pe orice funcție nouă din public. `REVOKE … FROM PUBLIC` nu atinge grant-ul explicit către `anon`/`authenticated` — exact motivul pentru care migrările existente din repo revocă explicit și de pe anon (ex. 20260912_fn_ofertare_cerinte_amprente.sql:34-35, comentariul din 20260912_ofertare_propunere_tehnica_v1.sql:116-117). Rezultat: `diurna_amprenta_canonica` (SECURITY DEFINER, sare peste RLS pe pontaj_records) e expusă prin PostgREST la /rest/v1/rpc/ oricui deține cheia anon (e în bundle-ul Vercel) și întoarce TEXTUL întreg `employee_id|data|diurna|norma` (inclusiv CO/CM) pentru orice angajați și orice interval — fără autentificare. `diurna_amprenta_hash` e la fel un oracle (poți verifica ipoteze despre pontajul cuiva). Și `diurna_salveaza_plata` păstrează grant-ul implicit pe anon (blocată doar de poarta de rol din cod, dar contrar intenției din :149-150).
- **Repro**: După aplicarea migrării (local): `SELECT grantee, routine_name FROM information_schema.routine_privileges WHERE routine_name LIKE 'diurna_amprenta%';` → apar `anon` și `authenticated`. Sau: `curl -X POST "$SUPABASE_URL/rest/v1/rpc/diurna_amprenta_canonica" -H "apikey: $ANON_KEY" -H "Authorization: Bearer $ANON_KEY" -H 'Content-Type: application/json' -d '{"p_employee_ids":[1,2,3],"p_month_start":"2026-09-01","p_month_end":"2026-09-30","p_tarif_text":"50"}'` → 200 cu liniile de pontaj.
