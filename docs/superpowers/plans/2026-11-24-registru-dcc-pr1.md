# Registru DCC — PR1 (BD) — Implementation Plan

**Goal:** Baza de date a registrului DCC: configurarea (ghiduri, contracte, proiecte DCC), registrul pe trei niveluri (serii → documente / file / anexe → revizii), istoricul brut, structura de mesaje și legături (pregătită pentru etapa B), RPC-urile de alocare / revizie / anulare / „copiat” / „confirm că am trimis” cu idempotență legată de conținut, formatorul de cod și de nume de fișier în SQL cu paritate exactă în JS. O singură migrare L15 v2, **NEAPLICATĂ**, cu revenire, probe PGlite, test pe clona 176 și probă de concurență pe un cluster dispensabil.

**Architecture:** BD = sursa unică (L19). Tabele noi `dcc_*`, toate cu RLS și DOAR `SELECT` pentru `authenticated` (nicio scriere directă pentru `anon` / `authenticated` / `service_role`); toate scrierile prin RPC-uri `SECURITY DEFINER` care verifică explicit `auth.uid()`, sub-modulul `executie_dcc` + nivelul, accesul pe proiect (`fn_executie_proiect_permis`, 20261209a) și operația — printr-o SINGURĂ funcție de drept (`fn_dcc_drept`). Contorul seriei se ia sub `FOR UPDATE` pe rândul seriei; cheile de intenție stau într-un tabel propriu, cu hash-ul parametrilor normalizați. Invariantele (unicitatea codului pe contract, imuabilitatea textului înghețat, tranzițiile de transport, interdicția de ștergere) sunt impuse de constrângeri și de triggere BEFORE, deci țin pe orice cale (L07). Formatorul de cod e o funcție SQL `IMMUTABLE` care primește formatul din ghid (jsonb validat); aceeași logică în `src/dcc/dccCod.js`, testată pe ACELAȘI tabel de cazuri scris de mână.

**Tech Stack:** PostgreSQL 17 (Supabase) + runnerul L15 v2 (`scripts/livrare_migrare.sh`, `docs/LIVRARE_L15_V2.md`); PGlite pentru proba locală (`scripts/pglite/`); psql pe clona 176 (coordonatorul) și pe un cluster PG17 dispensabil (concurența); vitest pentru formatorul JS. Fără librării noi, fără TypeScript.

## Decizii de construcție (propuse; review-ul le poate întoarce înainte de cod)

- **[D1] Citirea registrului e pe CONTRACT, scrierea pe PROIECTUL DCC.** Registrul (serii, documente, revizii, istoric, mesaje) se citește de oricine are `fn_dcc_drept(p, 'citire')` pe CEL PUȚIN un `dcc_proiecte` al aceluiași contract (codurile sunt ale contractului; omul trebuie să vadă numerele ocupate de celălalt proiect ERP). Scrierea pe un document cere dreptul pe `dcc_documente.proiect_dcc_id` al documentului. Alternativa (citire strictă pe proiectul documentului) se schimbă într-un singur loc: `fn_dcc_drept_contract`.
- **[D2] `mod_alocare` stă pe `dcc_contracte`, nu pe `dcc_proiecte`.** Domeniul numerotării e contractul (§4.2); dacă două proiecte ale aceluiași contract ar avea moduri diferite, alocările manuale ar putea ocupa numere din contorul automat. Pe o cheie de serie (contract, emitent, tematică, tip) cele două moduri nu se amestecă: `fn_dcc_aloca_manual` refuză dacă există seria inițializată, `fn_dcc_aloca` refuză pe un contract `manual`.
- **[D3] Filele se declară la alocare.** `fn_dcc_aloca(…, p_nr_file)`: `NULL` = document fără planșe (Rev0 pe document); `N ≥ 1` = filele 1..N, fiecare cu Rev0 (fără revizie la nivel de document). Un document creat fără file nu primește file ulterior (identitatea a ceea ce a plecat nu se schimbă); unul cu file primește file noi prin `fn_dcc_fila_noua`.
- **[D4] Limba Rev0 e parametru** (`p_limba`; `NULL` = `dcc_proiecte.limba_implicita`). Formatorul refuză dacă ghidul cere limba (în cod SAU în numele fișierului) și limba lipsește.
- **[D5] Calea serverului** (psql ca `postgres`, fără JWT, ca `fn_rest_decontat_server`): permisă DOAR pentru configurare (ghid / contract / proiect DCC), importul istoric și inițializarea seriilor — operațiile pe care chat-ul le face cu „da”-ul lui Răzvan în PR3. Alocarea, revizia, anularea, „copiat” și „confirmat” cer JWT (un om). Autorul pe calea serverului = `NULL` + `actor = 'server'`.
- **[D6] Emitentul la alocare = emitentul proiectului DCC.** `p_emitent` rămâne în semnătură (ca în §4.2), dar trebuie să fie egal cu `dcc_proiecte.emitent` (altfel `DCC_EMITENT_STRAIN`). Înregistrarea documentelor subcontractorilor (emitent propriu) = după PR3, prin altă operație.
- **[D7] Anularea cere nivelul `admin`** pe sub-modul (sau owner) și motiv nevid; revizia nouă / fila / anexa / copiat / confirmat cer `scriere` (editor / admin).

### Task 1: Formatorul de cod și de nume de fișier (JS + tabelul comun de cazuri)

**Files:**
- Create: `src/dcc/dccCod.js`

- Test: `src/dcc/dccCod.test.js`

**Interfaces:**
- Formatul (în ghid, `dcc_ghiduri.format_cod` și `dcc_ghiduri.format_fisier`, jsonb): un tablou ordonat de segmente `{"camp": <c>, "prefix": <text>, "cifre": <int|null>}`, cu `camp` ∈ `contract | emitent | tematica | tip | secventa | fila | anexa | revizie | limba`. `prefix` = textul pus înaintea valorii (separatorul și eticheta: `"-"`, `".Rev"`, `"."`, `"-A"`), din alfabetul `[-._A-Za-z]{0,6}`; `cifre` = completare cu zerouri (obligatoriu 5 la `secventa`, 1..3 la `fila` / `anexa`, absent în rest). Reguli de validare (`formatValid` / `fn_dcc_format_valid`): fiecare câmp cel mult o dată; `contract`, `emitent`, `tip`, `secventa`, `revizie` obligatorii în ambele formate; primul segment fără prefix.
  Exemplul formei DCC Lot 1 (§2): `[{contract,""},{emitent,"-"},{tematica,"-"},{tip,"-"},{secventa,"-",5},{fila,"-",2},{anexa,"-A",2},{revizie,".Rev"},{limba,"."}]` → `30-AAA-TM1-COR-00045.Rev0.RO`.
- Componentele: `{contract, emitent, tematica|null, tip, secventa, fila|null, anexa|null, revizie, limba|null}`. Un segment al unui câmp opțional NULL (`tematica` la MOM, `fila`, `anexa`) se omite ÎMPREUNĂ cu prefixul lui; `limba` NULL cu segment `limba` în format = eroare `DCC_LIMBA_LIPSA`; obligatoriu NULL = `DCC_CAMP_LIPSA`; `secventa` ∉ 1..99999, `revizie` < 0, `fila` / `anexa` peste numărul de cifre = `DCC_VALOARE_INVALIDA`.
- `export function codDcc(format, comp) -> string` (aruncă `Error` cu codul de mai sus).
- `export function titluScurtDcc(titlu) -> string`: diacriticele românești (ă â î ș ş ț ţ și majusculele) → ASCII printr-o hartă EXPLICITĂ (aceeași în SQL, `translate()`), orice alt caracter din afara `[A-Za-z0-9]` → `_`, `_` repetate → unul, fără `_` la capete, tăiat la 60 de caractere (apoi fără `_` final); gol → `DCC_TITLU_SCURT_GOL`.
- `export function numeFisierDcc(formatFisier, comp, titluScurt, ext) -> string` = `codDcc(formatFisier, comp) + "_" + titluScurtDcc(titluScurt) + "." + ext`; `ext` ∈ `^[a-z0-9]{1,8}$` după `toLowerCase()`, altfel `DCC_EXTENSIE_INVALIDA`.
- `export function formatValid(format) -> boolean`.
- `dccCodCazuri.json`: `{ "formate": {"lot1": […], "lot2_cod": […], "lot2_fisier": […], "dde": […]}, "cazuri": [{ "id", "format", "comp", "titlu_scurt"?, "ext"?, "asteptat"?, "eroare"? }] }` — minim 30 de cazuri: Rev0 / Rev1 / Rev12, MOM fără tematică, filă, anexă, filă + anexă, Lot 2 cu limba doar în numele fișierului, forma DDE cu limba înaintea reviziei, secvențe 1 / 100 / 199 / 99999, diacritice + caractere speciale + titlu de 80 de caractere în titlul scurt, extensie cu majuscule, fiecare eroare de mai sus.
