P1-01 — Inventarul clasifică automat conturi neaprobate ca ERP

supabase/migrations/20261118a_portal_teren_identitate.sql:234–240 — INSERT INTO public.conturi_tip

Codul:

SQL
CASE WHEN email IN (...) THEN 'teren'
     ELSE 'erp'
END

transformă orice utilizator Auth care nu se află în lista celor trei într-un cont ERP aprobat.

Este aceeași categorie de risc închisă în r7: un cont nou, neconfirmat de owner, nu poate primi clasificarea erp implicit.

Problema este demonstrată inclusiv de fixture:

supabase/tests/portal_e1_schelet.sql — pending@example.invalid; portal_e1_1a.test.sql:35–38

Fixture-ul pending@example.invalid primește erp, iar testul așteaptă succes.

Acest test demonstrează funcționarea implementării actuale, nu respectarea regulii de aprobare r7.

Corecție obligatorie:

Inventarul inițial trebuie să aibă o sursă verificabilă pentru clasificarea erp: conturi aprobate de owner sau o listă de migrare confirmată.

Un cont fără aprobare verificabilă nu poate primi automat erp.

Dacă se dorește corespondență completă auth.users ↔ conturi_tip, introduceți o stare/tip explicit neaprobat care determină refuzul tokenului, ori opriți migrarea până la reconcilierea tuturor conturilor.

Modificați fixture-ul pentru a demonstra că un cont pending nu devine authenticated.

Nu solicit hardcodarea UUID-urilor tuturor conturilor ERP. Solicit o clasificare bazată pe aprobare, nu pe excluderea celor trei adrese.

P1-02 — Poarta acceptă modificarea periculoasă a unei funcții PUBLIC existente

20261118a_portal_teren_identitate.sql:147–176, 203–211 — fn_portal_public_aprobat() și fn_portal_porti_lipsa()

Lista albă reține doar semnăturile celor 21 de funcții.

Scenariu concret:

O funcție aprobată, de exemplu public.gen_numar_transport(), este modificată ulterior.

Primește SECURITY DEFINER sau un corp care execută o operațiune privilegiată.

Semnătura și dreptul EXECUTE rămân neschimbate.

fn_portal_porti_lipsa() continuă să o considere aprobată.

Rezultat: posibil false-green al porții de izolare.

Faptul că 20 dintre funcțiile actuale sunt SECURITY INVOKER nu demonstrează că sunt inofensive. Un invoker poate efectua operațiuni permise fără granturi pe tabele sau poate apela funcții privilegiate deja accesibile.

Corecție obligatorie:

Baseline revizuit pentru fiecare dintre cele 21: semnătură, corp/definiție, prosecdef, proowner, proconfig și ACL.

Verificarea apelurilor tranzitive relevante, inclusiv EXECUTE dinamic, conform L15.

Orice schimbare semantică neaprobată → poarta roșie.

Test negativ: modificarea corpului sau conversia unei funcții aprobate în SECURITY DEFINER, fără schimbarea semnăturii, trebuie detectată.

Poarta nu trebuie să depindă doar de numele unei funcții.

P1-03 — Poarta verifică incomplet privilegiile efective ale rolului teren

20261118a_portal_teren_identitate.sql:178–218 — fn_portal_porti_lipsa()

Sunt verificate:

atributele rolului;

apartenența la authenticated, anon, service_role;

relațiile, secvențele și funcțiile din public;

dreptul CREATE în public.

Acestea sunt verificări utile, dar nu reprezintă suprafața completă de acces.

Scenarii nedetectate:

teren primește apartenență la alt rol privilegiat, fără să fie unul dintre cele trei testate.

teren primește USAGE și EXECUTE pe obiecte accesibile din storage, auth sau altă schemă expusă.

O funcție privilegiată din afara public devine executabilă pentru teren.

Apartenența necesară authenticator → teren este eliminată, iar poarta nu raportează configurația incompletă.

În anumite combinații, poarta poate continua să returneze {}.

Corecție obligatorie:

Verificați apartenențele efective și opțiunile SET/INHERIT față de o listă aprobată, plus privilegiile rolului în toate schemele relevante pentru API, Auth, Storage și module.

Nu trebuie eliminate drepturile PostgreSQL de sistem necesare funcționării normale. Este suficient un baseline precis cu excepțiile aprobate.

Adăugați teste negative pentru o schemă din afara public, o funcție privilegiată și o apartenență suplimentară.

P1-04 — Rollback-ul poate elimina funcția hook în timp ce Auth încă o utilizează

supabase/revenire/20261118a_portal_teren_identitate_ROLLBACK.sql — blocul $check$, apoi DROP FUNCTION public.fn_auth_token_hook(jsonb)

Rollback-ul verifică riguros datele și configurația obiectelor PostgreSQL create.

Dar nu verifică dacă acel Custom Access Token Hook a fost activat în configurația Supabase Auth.

Scenariu:

E1-1a este aplicat.

E1-1b/E1 ulterior activează hook-ul.

Obiectele SQL urmărite rămân nemodificate.

Se execută rollback-ul E1-1a.

Snapshotul poate corespunde, iar funcția hook este eliminată.

Auth continuă să invoce funcția inexistentă.

Rezultatul poate fi blocarea emiterii de tokenuri pentru toți utilizatorii.

Corecție obligatorie:

Rollback-ul E1-1a trebuie să fie permis doar când hook-ul este demonstrabil dezactivat și nicio componentă ulterioară nu depinde de obiectele eliminate.

Preflight-ul runnerului trebuie să verifice starea externă relevantă, nu doar catalogul PostgreSQL.

Dacă verificarea nu poate fi făcută, rollback-ul refuză.

După activarea hook-ului, revenirea trebuie orchestrată împreună cu procedura de urgență C1: blocare conturi teren, revocare sesiuni, verificare, dezactivare hook, apoi eliminare obiecte.

Rollback-ul SQL singur nu poate demonstra starea configurației Auth.
